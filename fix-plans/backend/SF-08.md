## Nguyên nhân

Order-service gọi hai đường dẫn mà promotion-service không có:

| Bên gọi (`PromotionServiceClient.java`) | Bên có thật (`PromotionController.java`) |
|---|---|
| `POST /validate` với body, dòng 18-19 | `GET /validate/{code}`, dòng 118-126 |
| `POST /usages` với body, dòng 21-22 | `POST /{code}/usages`, dòng 135-143 |

Đơn hàng chỉ biết `promotionId`, không biết mã. Lỗi Feign rơi vào `OrderServiceImpl.java:294-295` và trở thành `VALIDATION_ERROR`, nên trông như mã khuyến mãi không hợp lệ.

Lỗi thứ hai âm thầm hơn: `recordPromotionUsageBestEffort` (dòng 657-670) nuốt exception, nên số lượt dùng mã sẽ không bao giờ được trừ, kể cả khi đã sửa lỗi đầu tiên.

### 2. promotion-service: `service/impl/PromotionServiceImpl.java`, sau dòng 186

```java
    @Override
    @Transactional(readOnly = true)
    public PromotionValidationResponse validateById(Long promotionId, Long userId, BigDecimal orderSubtotal) {
        return priceIfUsable(getPromotionOrThrow(promotionId), userId, orderSubtotal);
    }

    @Override
    public PromotionUsageResponse recordUsageById(Long promotionId, Long userId, Long orderId) {

```

**Vì sao:** dùng lại `priceIfUsable` (dòng 250-265) và `recordUsage` nên toàn bộ quy tắc nghiệp vụ, retry và idempotent giữ nguyên, không có bản sao. `recordUsage` tự quản lý transaction bằng `TransactionTemplate`, nên gọi nội bộ vẫn đúng.

### 3. promotion-service: `controller/PromotionController.java`, sau dòng 143

```java
    // Order-service prices an applied promotion by id. Internal: discount data for any user id, so
    // gated by X-Internal-Token (InternalTokenInterceptor), same as the usages endpoints.
    @GetMapping("/{id:\\d+}/validate")
    @Operation(summary = "Service-to-service: validate/price a promotion by id"
            + " (requires the X-Internal-Token shared secret)")
    public ResponseEntity<ApiResponse<PromotionValidationResponse>> validateById(
            @PathVariable Long id, @RequestParam Long userId, @RequestParam BigDecimal orderSubtotal) {
        return ResponseEntity.ok(ApiResponse.ok(promotionService.validateById(id, userId, orderSubtotal)));
    }

    @PostMapping("/usages")
    @Operation(summary = "Service-to-service: record a redemption by promotion id"
            + " (requires the X-Internal-Token shared secret)")
    public ResponseEntity<ApiResponse<PromotionUsageResponse>> recordUsageById(
            @Valid @RequestBody RecordPromotionUsageRequest request) {
        PromotionUsageResponse response =
                promotionService.recordUsageById(request.promotionId(), request.userId(), request.orderId());
        return ResponseEntity.status(HttpStatus.CREATED).body(ApiResponse.ok(response));
    }
```

**Vì sao thêm endpoint thay vì để order-service gửi mã:** order-service chỉ lưu `promotionId`. Muốn gửi mã phải gọi thêm một lần để tra, hoặc đổi request `POST /orders` đang được storefront dùng đúng (`CheckoutScreen.tsx:120-122`).

**Vì sao `\\d+`:** tránh đụng với `/validate/{code}` hiện có khi mã có giá trị là `validate`.

`RecordPromotionUsageRequest` đã có đủ `userId`, `promotionId`, `orderId`, và các trường trùng với `RecordPromotionUsageFeignRequest`, nên không cần DTO mới.

## Kiểm thử lại

- Đặt hàng có mã hợp lệ: 201, tổng tiền đã trừ giảm giá.
- Mã hết hạn hoặc đã dùng: 400.
- Sau khi thanh toán thành công: lượt dùng mã tăng 1.
- Gọi `GET /api/v1/promotions/1/validate` qua gateway mà không có token nội bộ: bị từ chối với 401 hoặc 403.
- Chạy lại luồng 7 và các test case Blocked trong [HT Áp mã](../../storefront/ht-ap-ma.md), [HT Checkout](../../storefront/ht-checkout.md).
- `./mvnw.cmd spotless:apply`, `./mvnw.cmd clean verify` trong `promotion-service` và `order-service`.
